## 1 这一期做了什么

**后端：安全解压**（`apps/api/app/archive.py` + `POST /api/drive/extractions`）。

计划 §7.2 的规则全部落地，且实现方式与"先解压到临时目录再原子移动"是**同一个意图在节点树上的等价物**：
**扫描阶段不写任何东西**（不落节点、不写对象），全部通过后才落库；中途失败则**补偿清理**（把已建出来的
节点 trash + purge，对象按引用计数删）。用户看到的要么是完整结果，要么什么都没有——不存在"解了一半"。

| 攻击面 | 处置 | 错误码 |
| --- | --- | --- |
| Zip Slip（`../`）、绝对路径、盘符 `C:`、UNC `//` | 拒绝整份 | `archive_path_unsafe` |
| zip symlink（外部属性 `0o120000`）、tar symlink/hardlink/字符设备/FIFO | 拒绝整份 | `archive_path_unsafe` |
| 控制字符、超长段、超深（>32 层）、Windows 保留名、尾随点/空格 | 拒绝整份 | `archive_path_unsafe` |
| 条目数 >2000 | 拒绝 | `archive_too_many_entries` |
| 单文件 >64MB / 解压总量 >512MB | 拒绝 | `archive_uncompressed_size_exceeded` |
| 压缩比 >200:1（zip bomb） | 拒绝 | `archive_ratio_exceeded` |
| 归档内路径重复 / 文件与目录同名 | 拒绝 | `archive_target_conflict` |
| `.7z/.rar/.bz2/.xz` | 只识别不解压 | `archive_format_unsupported` |
| 空归档 | 拒绝 | `archive_empty` |
| 嵌套归档（`inner.zip`）、`__MACOSX/`、`.DS_Store` | **跳过并如实计数**（`skipped_nested` / `skipped_junk`） | — |
| 目标目录同名 | 自动加 `-2` 后缀（不覆盖、也不失败） | — |

配额在**整份解压**上一次性过闸：一次过不了就整份拒绝，不会解到一半说空间不够。

**前端：`/drive` 从"平铺列表"改成文件管理器**（`apps/web/app/drive/page.tsx` + 新增 `drive.css`）。

- 目录导航（面包屑可跳、双击进入、单击看详情）；搜索（后端名字子串）、排序（名称/上传/修改/大小）、
  分页（游标 + "加载下一页"）；
- 新建文件夹、上传（**拖拽 + 点击，XHR 真进度**）、下载、改名（行内）、移动（目录选择弹窗）、复制、
  删除（→ 回收站）；批量选择（全选 + 批量移动/删除）；
- 回收站视图：恢复 / 彻底清除（各自二次确认，文案写明"恢复回原目录""彻底清除才释放空间"）；
- 安全解压入口：压缩包行上的解压按钮 → 完成后任务栏如实汇报"N 个文件、M 个目录、跳过嵌套 K 个"；
- 详情抽屉：路径、内容 sha256、修订、上传/修改时间、来源成果物、项目引用、**最近操作（审计）**、
  一行操作按钮（下载/解压/改名/移动/复制/加入项目/转换入知识库/删除）；
- 保留旧功能：上传、加入项目、转换入知识库都在（老接口继续可用）；
- 移动端（≤900px）：名称列吃掉剩余宽度、大小/时间收进行内标签、行操作换行、抽屉整宽。

**为什么样式单独放 `app/drive/drive.css`**：`globals.css` 当时有并行改动在途，页面级样式没必要挤进去
（App Router 支持页面直接 import CSS）。类名统一 `drive-` 前缀。

## 2 浏览器实机验收（真跑，不是"看起来能用"）

在真浏览器里（本地 API + 本地 Web，临时库）走完了全流程，并**抓出两个真缺陷**：

1. **每次渲染都重新拉一次目录**：`loadNodes/loadTrash` 的 `useCallback` 依赖含 `notify`（工作区上下文每次
   渲染都换 identity）→ 依赖不稳定 → `useEffect` 每渲染重跑 → 请求风暴，且**刚点开的控件会被下一次渲染
   换掉**（表现是"点了没反应"）。修法：读取函数依赖置空、变化的值（搜索词/排序/notify）走 ref。
2. **页面里两片空白**（截图一眼可见）：全局 `.page-content` 是 grid，**行会把容器剩余高度按份分掉**——
   指标卡被撑到 214px（内容只有 ~90px）；同时全局 `input, select, textarea { width: 100% }` 把面板头部的
   排序下拉拉成整行、把工具条撑成三行高。修法：本页作用域内 `align-content: start` +
   `grid-auto-rows: min-content` + 给工具条下拉写死宽度（**没有**去动共享的 `globals.css`）。

验收走到的每一步（都通过）：新建文件夹 → 双击进入（面包屑 `个人云盘 / 论文素材`）→ 拖拽上传（进度 100%、
行上显示 sha256 与修订）→ 搜索"甲"命中且清空后恢复 → 批量选择（"已选 N 项"）→ 移动到…弹窗（列出子目录、
确认后任务栏写"已移动 N 项到 …"）→ 上传 zip 并解压（"解压完成：2 个文件、3 个目录"）→ 详情抽屉
（路径/sha256/来源/项目引用/最近操作 upload）→ 删除 → 确认框 → 回收站列出 → 恢复 → 再删 → 彻底清除
（确认框 + "已彻底清除"）→ 1280/900/390px 三档视口**均无横向溢出**、上传按钮都在视口内。

## 4 与计划的偏差 · 未做

- **解压不递归**：嵌套归档只识别与跳过（计划明确"默认不递归解压"），没有开关。
- **批量下载没做**：批量操作给的是"移动/删除"；多选下载在浏览器里会触发多次下载，体验与权限都更麻烦，
  等有真实需求再说。
- **解压是同步请求**：大归档会占着一个请求（上限 512MB/2000 条目，实测小包毫秒级）。要做异步任务队列
  属 FM-6（"传输历史、失败原因和重试"）。
- **上传没有断点续传**：计划里"大文件走 Multipart/断点上传"归 FM-6。
- **未部署**：本地验收完成后没有跑 `server_release.sh`（按纪律"未明确要求不主动部署"）。
