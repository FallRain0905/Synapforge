## 1 结论先说

能做，但要分清**三种"更好"的代价不一样**：

| 想要的 | 今天的状态 | 做到它要付什么 |
| --- | --- | --- |
| **执行细节可见** | ✅ 已经在做：`process.started / tool.completed / file.changed / agent.message` 逐条实时回传，右栏抽屉里能看到 | 零成本（已上线） |
| **思考（thinking）可见** | ❌ 没开：opencode 的思考块默认不输出到事件流 | **小**：`opencode run --thinking` 会让它吐思考块；内核解析成新的过程事件 `agent.thinking`，平台存/转发，页面折叠展示。**需要先采一份真实样本确认事件形状**（不猜协议） |
| **计划模式 / 思考强度** | ❌ 没做：模型之外的模式与推理强度都没暴露 | **小**：CLI 已有 `--agent`（选择 agent/模式）与 `--variant`（provider 的推理强度，如 high/max/minimal）。做法与模型切换同构：内核探测 `opencode agent` 列表 → 心跳上报 → 页面下拉 → 每轮把 `--agent/--variant` 插进模板（与 `-m` 同一条路径，内核已有插入点） |
| **逐字流式回复** | ❌ 做不到：`--format json` 是**事件级**（一段 text 一条事件，不是 token 流） | **大**：要改用 opencode 的**服务端接口**——常驻一个 `opencode serve`，通过它的 SSE 事件流（`message.part.updated` 之类）拿增量。这等于换一条执行通道：内核要管"每工作目录一个常驻 server + 订阅 + 会话映射 + 断线重连"，平台要加一种 `delta` 帧。**这是独立一期**，不是加个参数 |

**一句话**：思考/模式/强度是"加参数 + 加探测"的事（一天量级）；**逐字流式是换通道**（一周量级，且会碰内核最脆弱的部分）。

## 2 这四件事分别怎么落

### 2.1 思考可见（M-5a，建议先做）

1. **采样本**：在云端执行体上跑一次 `opencode run --format json --thinking "<让它想一下再答>"`，看思考块在事件流里的形状（`part.type == "reasoning"`？还是别的字段）。
2. 内核：`parse_opencode_jsonl` 识别思考块 → 新过程事件 `thinking`（与 `agent.message` 并列）。
3. 平台：轮次事件表已能存任意 `event_type`（`agent_turn_events`），**不需要迁移**；白名单是内核侧的 `SessionIpcEvent` Literal——**注意**：轮次事件走的是 HTTP `/api/agent/turns/{id}/events`（不是 Gateway 白名单），所以这里没有协议改动。
4. 页面：右栏抽屉里把思考块折叠显示（默认收起，点开看），并给一个开关"显示思考"。

### 2.2 agent 模式（计划模式）与思考强度（M-5b）

1. 内核探测：`opencode agent`（列出可用 agent，如 plan/build）与可选 `--variant` 取值（variant 是 provider 相关的，未必能列全——**列不全就让人手填**，不编）。
2. 心跳 `resource_summary` 增加 `agents: ["plan","build"]`（与 `models` 并列）。
3. 会话级设置：`agent_conversations` 加 `agent_mode` / `reasoning_variant` 两列；页面在工具条上加两个小下拉（与模型下拉同排）。
4. 内核：`build_chat_command` 已经支持在 `{prompt}` 前插 `--session`/`-m`；再加 `--agent`/`--variant` 两个可选插入（同一处、同一规则，测试已有覆盖点）。
5. "计划模式"的语义**由 opencode 的 agent 定义**（plan agent 只读不写之类），平台不自己发明——页面上标注"模式由执行体的 agent 定义"。

### 2.3 逐字流式（M-5c，独立一期，需要拍板）

两条路，只能选一条：

- **A. 常驻 `opencode serve` + SSE**（真流式）：内核为每个工作目录维护一个 server（或全局一个），执行轮次时订阅 `/event`；把 `message.part.updated` 的增量转成平台的 `delta` 帧；页面按 token 追加。
  代价：内核多一层进程生命周期管理、平台多一种帧、要处理 server 崩溃/重启与会话映射；好处：真逐字 + 顺带拿到**工具实时状态**与**权限请求**（可以做成"待批准"卡片，取代现在的 `--auto` 全自动）。
- **B. 保持现状 + 更细的分段**：`--format json` 下 opencode 每完成一个"part"就发一条 text；长回答天然分成多段。我们只需**让这些段在生成时立刻显示**（现在就是立刻回传的，但页面只在轮次结束后才把正文放进气泡——**这一条是可修的**）。
  代价：小；好处：看起来像"分段流式"而不是"等到最后一次性出现"。**这是今天就能落地的改进。**

**建议**：先做 B（把正文在过程中就显示出来，而不是等 complete），把 A 作为 M-5c 单独评估。

### 2.4 复刻到哪一层为止（明确不做）

- **不做**：完整 TUI 复刻（终端内嵌、快捷键体系、多标签）、本地模型托管、把 opencode 的插件/权限系统整套搬进平台。
- **做**：模型 / 会话 / 附件 / 中断（已完成）+ 思考 / 模式 / 强度 / 分段流式（M-5a/b + B）。这已经覆盖日常用 opencode 的高频动作。

## 5 验收口径（怎么做才算完成，先说好）

- 思考：一次真跑里，右栏能看到思考块；关掉开关后看不到；**不假装**（拿不到就不显示"思考中"）。
- 模式/强度：切换后，该轮的命令模板里确实带上了 `--agent/--variant`（跑一次、看执行体日志里的命令行）。
- 分段流式（B）：长回答过程中，页面每几秒多出一段；**不谎报**为"逐 token"（文案写"分段"）。
- 真流式（若拍板 A）：`delta` 帧在浏览器 Network 里可见；断线后历史可补齐。
