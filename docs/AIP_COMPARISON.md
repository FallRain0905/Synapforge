## 2. AIP 是什么（基于公开材料的准确描述）

- **名称**：AIP = Agent Interconnection Protocol，中文「智能体互联协议」，社区自称「智联协议」。
- **定位**：为**跨厂商、跨平台**的智能体互联提供一套**最小功能集合 + 功能间接口**的标准；不约束具体技术形式（集中式、分层式、分布式皆可），目标是"厂商只要实现这些功能与接口就能互相联通"。
- **六（七）大模块**：总体架构、身份码、身份管理、智能体描述、智能体发现、智能体交互、智能体工具调用。
- **参考实现**：北邮 ACPs 协议族采用"分层集中"方案——自治域内用注册服务器、身份凭证管理与验证服务器、发现服务器；用消息队列做消息分发以支持**群组通信**（比点对点效率高）；并称可**兼容已采用 A2A / MCP 的智能体与工具**。
- **状态**：协议族首版代码 2025-10-27 发布，持续征集试点应用单位；社区规模小（站点显示 152 成员 / 20 仓库 / 6 收录仓库）。

## 3. 七部分要点（压缩版）

> 详细摘录见 `docs/reference/aip/standard-notes.md`（每条都带原文出处链接）。

1. **总体架构**：给"智能体互联所需的功能"而不是具体实现；区分**局域系统**（自有生态内运行）与**广域系统**（开放组件接口融入大生态）。
2. **身份码**：由"身份管理功能提供方"分配；区分**智能体程序包序列号**（程序包级，注册审核后分配）与**智能体实例序列号**（实例级，自动审核）；自控范围内允许用自定义编号，需要时与身份码建立映射。
3. **身份管理**：三个功能实体——**身份注册方**（审核并分配身份码）、**凭证发行方**（签发/管理/验证身份凭证）、**身份验证方**（自验或委托独立验证方）；附录给 CA 证书的参考实现。
4. **智能体描述**：对外描述=**属性表**（访问地址、访问方法、认证方法、**技能列表**）+ **技能表**；定义注册流程与能力发布过程。
5. **智能体发现**：两种方式——**平台式发现**（独立发现平台从描述管理平台取注册能力信息，做匹配与推荐）与**预置信息式发现**（无发现平台时，用本地缓存的能力信息自行匹配）；产出都是"与需求能力匹配的智能体列表"。
6. **智能体交互**：三种模式——**点对点 / 群组 / 混合**；交互要素为**数据、消息、任务、会话**；附录 A 三种点对点实现（远程调用、流式、通知），附录 B 三种协作模式（主从、代理协商、**任务订阅**）。
7. **智能体工具调用**：解读页已 404；《能力互联》一文提到其目标是把工具调用纳入**统一接口范式**，让模型、API、外部资源与"人在环"在**同一事务**里协作与回滚，使能力组合"可复演、可审计、可清算"。

**《能力互联》补充的几个概念**（对产品化最有参考价值的一段）：
- 能力被抽象为**标准化服务单元**：清晰的输入/输出 + **服务质量合约（SLA）** + 可观测日志与**证据链**；
- **意图对象**表达目标、约束、**预算**、时限与**证据要求**；
- 身份码与**公钥绑定**，支持签发/轮换/吊销；
- 发现侧建议"权威注册目录 + 语义索引 + **结构化硬过滤** + 评测与**信誉分**"；
- 明确把"人类专长"也封装成可寻址、可计价、可审计的能力。

## 4. 与 synapforge 的对照（一眼看懂差别）

| 维度 | AIP 的取向 | 我们的现状 |
| --- | --- | --- |
| 目标场景 | **跨厂商开放互联**（不同公司的智能体互通） | **单组织内闭环协作**（一支队伍 + 几台自己的机器） |
| 身份 | 身份码 + CA 凭证 + 注册/发行/验证三方可能分离 | 设备 Ed25519 公钥指纹 + 设备令牌（只存哈希）+ 项目能力令牌；注册即绑定 |
| 描述 | 机读的**属性表 + 技能表**（地址/方法/认证/技能） | Agent 自报 tools ∪ 设备声明的 capabilities；**自由字符串**，无版本、无输入输出 |
| 发现 | 平台式发现 + 预置信息式发现，产出候选列表 | 派单/领取时按 `required_capabilities` **硬过滤**；`/team/capabilities` 给"没人能跑"告警 |
| 交互 | 点对点/群组/混合；远程调用/流式/通知；主从/代理协商/任务订阅 | 自有协议：拉取式 claim→progress→result + 租约心跳 + 网关逐帧应答（协议是仓库禁区，不能动）；群聊由服务端从事件派生卡片 |
| 工具调用 | 统一接口、事务化、可回滚、人在环 | `worker_executor`：codex（协议适配）/ cli（提示词驱动模板）/ 声明式命令；执行有信息边界与证据链 |
| 治理/计费 | 面向"可计价、可清算" | 面向"可追溯、可复核"（门禁、风险、交接收据） |

## 5. 可借鉴清单（按落地性价比排序）

**值得借鉴（改造成本低、收益明确）**

1. **智能体描述结构化 → "能力卡"**：把我们现在自由字符串的能力，升级为 `{技能名, 版本, 输入, 输出, 说明}` 的机读描述（AIP 的"技能表"思路）。直接解决我们已经踩到的坑：`python` 与 `Python` 被当成两种能力、能力词表无版本。落点：`store.capability_catalog()` + `/team` 的能力目录页 + Agent 注册/心跳的自报字段。
2. **发现产出"候选列表 + 推荐"而不是布尔过滤**：AIP 的发现是"匹配出候选智能体列表"，我们目前只有"能/不能领"。落点：`/team/capabilities` 的"没人能跑"旁边，加"这几台能跑（按负载/成功率排序）"；W-3 调度器的派单选择已按负载，补上"成功率/信誉"即可。
3. **身份拆成"包序列号 + 实例序列号"两段**：我们现在的 `agent_id` 把"哪种执行体"和"哪个实例"混在一起，统计"同一执行体的多实例"要做字符串猜测。落点：`agents` 增加 `package_id`（执行体类型/版本）+ `instance_id`，设备注册时由平台派生。
4. **意图对象的两个缺项：预算 与 证据要求**：任务已有 `acceptance_criteria`（约束）、`deadline`（时限）、`information_boundary`（合规/边界），但**没有预算**（这次执行最多花多少 token/时间/次数）和**显式证据要求**（必须附哪类证据才算完成）。落点：`TaskCreate` 加 `budget`、`evidence_requirements`，门禁校验时消费。
5. **"信誉分"用我们已有的数据做**：吞吐接口（`/team/throughput`）已经有按成员的完成/失败统计，AIP 的"评测与信誉分"对我们就是把它做成**派单权重**（失败多的排后面）。

**可以借鉴表述、但实现上我们已有等价物（用于对外材料）**

6. "能力组合要可复演、可审计" —— 我们的成果物哈希 + 运行记录 + 证据链 + 门禁已经是这套东西；对外可以这么说。
7. "任务订阅模式" —— 我们的 claim + 租约 + 心跳本质就是订阅；"通知实现方式"对应我们的 WS 广播。
8. "同事务回滚" —— 我们的任务状态机 + 执行体边界（读/写允许清单）是同一意图的另一种做法。

**暂不适用 / 不建议照搬**

9. **交互层报文**：AIP 的会话/消息/任务模型要替换我们自己的 agent 协议才能"讲同一种话"，而我们的协议是仓库禁区（信封与序号固定），照搬会破坏既有接入的机器。若真要互通，正确做法是**加一层 AIP 网关做协议翻译**（对外说 AIP，对内仍旧协议），而不是改内核。
10. **CA 三方分离的完整体系**：单组织闭环里收益很低（我们已经有设备公钥指纹 + 令牌轮换/吊销），除非未来要把平台开放给外部组织接入。
11. **可计价/可清算**：不做商业化前没有必要。

## 6. 如果要真接入 AIP，最小可行路径（供后续参考，不是本轮承诺）

1. **描述层**：加 `GET /.well-known/aip/agents`（或等价路由），按 AIP 属性表输出我们已有的事实——访问地址、访问方法（拉取式领取）、认证方法（设备令牌/项目能力令牌）、技能列表（来自能力卡）。**纯新增读接口，不动内核**。
2. **发现层**：平台内已有的能力目录 + 负载/成功率，包装成"发现服务"的返回结构（候选列表 + 匹配理由）。
3. **身份层**：把设备公钥指纹/身份码按 AIP 的身份码规则**映射**（我们保留自有编号，对外提供映射字段——这正是 AIP 允许的"自控范围内自定义编号 + 需要时映射"）。
4. **交互层**：保持自有协议，由 AIP 网关做翻译；先在"点对点 + 任务订阅"这一对最接近我们的模式上试点。
