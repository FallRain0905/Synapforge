# synapforge 项目现状与预期修改计划

> 文档状态：产品重新定位后的规划基线
>
> 记录日期：2026-09-26
>
> 适用范围：单 Agent 工作台、多 Agent 协作生产、垂直领域自动化工作流包、项目工作区与 Agent 执行链路
>
> 本文用于统一产品定位、用户场景、建设优先级和暂缓事项。它不替代具体期次的技术实施计划；每次进入实施前，仍需另行确认范围、协议影响、迁移方案和验收口径。

## 1. 核心产品决策

synapforge 的核心定位是：

> **一个 Agent 协作生产平台。它提供主流的单 Agent 工作体验，也支持多个 Agent 按任务、能力和交接协议协作完成项目，并通过垂直领域工作流包和自定义编排，把复杂生产过程自动化。**

产品由三层组成：

```text
单 Agent 工作台
    ↓
多 Agent 协作生产
    ↓
垂直领域自动化工作流包
```

三层的关系如下：

1. **单 Agent 工作台是基础入口。** 用户应能像使用主流 Agent 产品一样直接对话、上传文件、查看流式过程、接受权限请求、让 Agent 修改或生成文件，并继续多轮工作。
2. **多 Agent 协作是平台的核心差异。** 多个 Agent 必须能在同一项目中分工、并行执行、形成成果物、提交结构化交接、等待上游批准并继续推进，而不是几个单 Agent 页面并列存在。
3. **垂直工作流包是规模化能力。** 数学建模、长文写作、PPT 制作、研究分析等属于工作流包。工作流包定义阶段、任务、角色、提示词、输入输出、交接规范、审核门槛、失败策略和交付方式。

数学建模不是平台一级定位，而是当前首个成熟的垂直领域工作流。CUMCM 模板、审题、建模、编程、实验、论文装配等能力应保留，但必须放在通用工作流平台之下。

## 2. 明确暂缓的 Git 决策

### 2.1 当前决定

**Git 相关产品功能暂缓开发。** 平台不建设 GitHub 的替代品，也不重复实现仓库托管、Pull Request、代码审查、分支协作、推送和拉取等 GitHub 已经成熟提供的能力。

用户可以直接使用 GitHub 完成：

- 创建和托管仓库；
- 上传代码；
- 创建分支；
- 提交 Pull Request；
- 进行代码审查；
- 合并分支；
- 使用 GitHub Actions 或其他 CI；
- 通过现有 Git 客户端同步代码。

平台当前的价值不在于替代 GitHub，而在于 Agent 协作生产本身：任务编排、执行体接入、过程记录、成果物、结构化交接、证据、审核门禁和工作流自动化。

### 2.2 暂缓范围

本阶段不新增以下用户-facing 功能：

- GitHub 仓库导入向导；
- 平台内置仓库浏览器；
- 平台内置分支管理；
- 平台内置 Pull Request；
- 平台一键提交或推送 GitHub；
- 以平台项目工作区替代用户的 Git 工作区；
- 为了 Git 协作重新设计一套代码版本审批系统。

已有的 Git 索引、commit 关联、文件快照或执行体工作目录能力，如果已经被成果追溯、运行审计或 Agent 执行内部使用，可以继续保留；它们属于平台内部的可追溯基础能力，不代表本阶段要把 Git 扩展成新的产品模块。

### 2.3 后续重新评估条件

只有在以下需求被真实用户反复验证后，才重新评估 Git 集成：

- Agent 执行需要稳定、隔离的代码输入输出；
- 用户无法通过 GitHub 工作流解决 Agent 工作区同步；
- 任务、Run、成果物与 commit 的关联成为高频刚需；
- GitHub 外部操作造成明确的生产断点；
- 能够证明新增能力不会重复建设 GitHub 的仓库和 PR 产品。

重新评估时优先考虑轻量集成，例如读取用户提供的仓库地址、记录 commit URL、保存任务与外部 PR 的关联，而不是在平台内复制 GitHub。

## 3. 当前项目现状

### 3.1 单 Agent 工作台

当前 `/my-agent` 已经具备单 Agent 产品的较好基础：

- 多轮会话和历史恢复；
- 常驻 `opencode serve` 通道和真实增量显示；
- reasoning 与最终答案分离；
- 默认折叠的思考过程；
- 角色、模型和推理强度相关能力；
- Markdown、表格和数学公式渲染；
- 附件输入与执行体工作目录 `inputs/`；
- 对话产出文件、下载和转入云盘；
- 权限请求卡片；
- 真正的停止执行；
- 角色定义指纹和漂移提示；
- 移动端会话抽屉、焦点管理和受控滚动。

当前主要问题不是基础能力完全缺失，而是产品闭环还不够明显：

- 用户可以对话，但不容易把对话结果转成正式项目任务；
- 对话产出与成果物、任务、审核之间的关系不够明显；
- `/my-agent`、项目工作区聊天和旧 `/ask` 页面曾经形成多入口心智负担；
- 没有 Agent 时，页面虽然能说明原因，但下一步入口不够直接；
- 单 Agent 页面已经接近主流体验，却还没有成为平台的清晰第一入口。

### 3.2 多 Agent 协作生产

后端和领域模型已经具备多 Agent 协作的主要基础：

- Project、Task、Run、Artifact、Handoff、Evidence、Review、Gate、Event；
- 设备注册、Gateway、项目能力授权；
- manual、hybrid、auto 三种任务模式；
- 能力匹配、任务领取、租约和心跳；
- 任务依赖与已批准成果物作为下游输入；
- 成果物版本、哈希、证据绑定和人工批准；
- 结构化交接和交接收据；
- 运行过程、用量、预算和信息边界记录；
- 工作区聊天、任务、成果空间和概览 Tab；
- 云端执行体已接入并真实跑通任务与成果物链路。

但当前多 Agent 仍然更像“多个功能对象已经存在”，还不像一个用户能一眼理解和验证的协作生产系统：

- 工作区默认仍偏聊天，分工、并行、交接和阻塞不够突出；
- Agent 的项目角色、当前任务、负载、下一步和交接状态没有形成统一视图；
- 用户需要在工作区、任务页、我的任务、运行控制台、交接中心、成果物库和审核页之间自行拼接过程；
- 成果物、交接和下游任务之间的因果关系不够明显；
- 目前缺少覆盖两个或三个 Agent 的稳定端到端协作验收；
- 任务成功、Run 完成、成果物上传成功、成果物待审和成果物批准仍容易被误解成同一个“完成”。

### 3.3 垂直领域自动化工作流包

当前已经存在 CUMCM 数学建模模板包和相关能力：

- 四问任务 DAG；
- 任务和成果物骨架；
- 题面事实、问题拆解、建模、编程、实验、复核、论文装配和交付阶段；
- 模板渲染、边界审计、模板校验和交付检查；
- 数学建模 Agent 角色预设；
- 文档版本、评论、快照和协作编辑；
- 论文装配、编译和提交包流程。

当前主要问题：

- “模板包”仍然容易被理解成数学建模专属功能，而不是通用工作流包；
- “一键应用”容易让用户误以为已经得到完整结果，实际生成的是任务和成果物骨架；
- 工作流包的阶段、角色、输入输出、交接规范和人工介入点还没有以统一模型呈现；
- CUMCM、文档写作和未来 PPT 工作流之间还没有清晰的共用抽象；
- 自动模式目前主要负责受限派发，不等于自动完成、自动审核和自动交付；
- 用户自定义自动化模板的能力还没有成为可用产品。

### 3.4 当前产品层级问题

目前导航和页面仍混合了三种不同层级：

```text
单 Agent：我的智能体、旧问答入口
项目协作：工作区、任务、成果物、审核、交接、运行
工作流工具：数学建模模板、知识库、图谱、论文交付
```

这些页面都能访问，但产品没有足够明确地告诉用户：

- 哪些是平台的基础能力；
- 哪些是多 Agent 协作的核心体验；
- 哪些只是某个领域的工作流工具；
- 当前用户应该从哪里开始；
- 一次普通 Agent 对话如何进入正式生产；
- 一个工作流包如何驱动多个 Agent 协作。

## 4. 目标产品结构

建议形成以下产品心智模型：

```text
Agent
  ↓
协作项目 / 工作区
  ↓
任务、Run、成果物、交接、审核
  ↓
工作流模板驱动的自动化生产
  ↓
文档、代码、PPT、论文或其他交付物
```

用户第一次进入平台时，应能看到三个清晰入口：

### 入口 A：开始一个 Agent 工作

适用于用户想直接完成一项工作：

```text
选择 Agent
→ 输入任务
→ 查看实时过程
→ 上传或生成文件
→ 多轮修改
→ 下载结果或转入项目生产
```

页面要明确提供两个后续动作：

- 继续对话；
- 转入项目生产。

“转入项目生产”至少应能创建任务、保存成果物、关联附件、选择下一个 Agent 或套用工作流。

### 入口 B：组建 Agent 协作项目

适用于多人和多个 Agent 共同完成一个目标：

```text
创建项目
→ 邀请成员
→ 接入并授权各自 Agent
→ 拆分任务
→ 并行执行或接力执行
→ 上传成果物和交接包
→ 审核与修订
→ 汇总和交付
```

这个入口要让用户看到“团队正在生产什么”，而不只是看到聊天消息。

### 入口 C：运行一个自动化工作流

适用于长周期、重复性、阶段明确的生产任务：

```text
选择工作流包
→ 填写项目输入
→ 生成任务图和 Agent 角色
→ 按依赖执行
→ 交接与审核
→ 失败重试或人工介入
→ 生成最终交付物
```

数学建模、长文写作、PPT 和研究分析都属于入口 C 的具体模板。

## 5. 重点用户场景

### 5.1 多人项目：每个成员都有自己的 Agent

用户目标：很多人一起做同一个项目，每个人的 Agent 负责自己的任务，完成后按平台协议上传成果和交接文档。

理想流程：

```text
创建项目
→ 邀请成员
→ 成员分别接入自己的 Agent
→ Agent 获得项目范围授权
→ 项目负责人创建并派发任务
→ 各 Agent 自动领取自己负责的任务
→ Agent 执行并上传成果物
→ Agent 上传结构化交接文档
→ 下游 Agent 读取已批准成果和交接
→ 人工或独立复核 Agent 审核
→ 下游任务继续推进
```

每个 Agent 的完成结果至少应包含：

- 任务完成摘要；
- 正式成果物和版本；
- Run 与用量；
- 证据和来源；
- 已完成内容；
- 未完成内容；
- 风险和待确认事项；
- 交接目标和建议下一步。

用户在项目工作区应能直接看到：

```text
Agent A：资料检索       已完成，等待审核
Agent B：方案设计       执行中
Agent C：代码实现       等待上游成果
Agent D：独立复核       待接收交接
```

这条场景是多 Agent 核心价值的主要验收场景。

### 5.2 长任务自动化：数学建模和多轮调试

用户目标：一个长周期任务按照预定模板自动推进，过程中进行多轮建模、代码、审计和调试。

理想流程：

```text
选择数学建模工作流
→ 填写题面、资料和约束
→ 生成阶段任务图
→ 分配审题、建模、编程、实验和复核角色
→ Agent 按依赖执行
→ 代码运行失败时重试或交给调试角色
→ 独立 Agent 复核假设、代码和结果
→ 人工处理关键门禁
→ 生成论文或提交包
```

这里的关键不是“一键生成答案”，而是“一键启动一条受约束、可中断、可复核的生产流程”。

工作流包必须明确：

- 每个阶段的输入和输出；
- 推荐角色和工具权限；
- 任务依赖；
- 交接字段；
- 自动重试条件；
- 人工介入点；
- 哪些结果可以进入下一阶段；
- 什么条件才算最终交付。

### 5.3 直接使用正常的网页 Agent

用户目标：像使用主流 Agent 产品一样完成一项个人工作，不必先理解任务板和工作流。

理想流程：

```text
打开 Agent 工作台
→ 选择执行体、模型或角色
→ 输入问题
→ 查看正文增量和思考过程
→ 上传文件
→ 让 Agent 阅读、修改或生成内容
→ 多轮追问和修订
→ 下载结果或转入项目生产
```

这个场景是平台的最低理解成本入口。用户可以先获得单 Agent 价值，再逐步进入多 Agent 和工作流。

### 5.4 用户自定义自动化编排

用户目标：自己创建一套生产模板，定义整体流程、每个阶段的目标、提示词和交接规范。

理想的模板定义包括：

```text
模板名称和适用场景
→ 阶段与任务节点
→ 顺序、依赖和并行关系
→ 每个节点的目标
→ Agent 角色和能力要求
→ 系统提示词与任务提示词
→ 工具权限
→ 输入输出格式
→ 成果物类型
→ 交接规范
→ 证据要求
→ 审核门槛
→ 重试和失败策略
→ 人工确认点
→ 最终交付方式
```

模板必须版本化。已运行项目绑定模板版本，模板后续修改不能悄悄改变历史运行的解释。

## 6. 预期修改计划

### 阶段 0：产品基础重定位

目标：让界面、文案和导航先表达正确的产品层级。

主要工作：

- 将对外定位统一为“Agent 协作生产平台”；
- 将数学建模明确为首个垂直工作流包；
- 调整首页为三个入口：单 Agent、协作项目、自动化工作流；
- 调整导航顺序，优先展示项目总览、项目工作区和 Agent 工作台；
- 统一“任务、Run、成果物、交接、审核、交付”的状态解释；
- 明确“模板骨架不等于完成结果”；
- 将“自动”解释为受约束的调度和推进，不承诺完全无人值守；
- 明确 `/ask` 与 `/my-agent` 的唯一入口关系，避免两套聊天产品并存。

验收重点：

- 新用户能在首屏理解三种使用方式；
- 不进入数学建模模板也能开始正常 Agent 工作；
- 用户能区分单 Agent 对话和正式项目生产；
- 用户不会把模板应用误认为已经得到最终答案。

### 阶段 1：单 Agent 工作台产品化

目标：把单 Agent 体验做成平台可信、顺滑的基础产品。

主要工作：

- 保持真实流式、思考、权限和停止语义；
- 让附件输入、文件产出、下载和转入项目生产形成连续路径；
- 增加“保存为成果物”“创建任务”“交给另一个 Agent”等明确动作；
- 无执行体时直接提供接入入口；
- 统一会话、角色、模型、执行体和权限状态的显示；
- 为失败、取消、上传失败和权限超时提供真实状态；
- 补充单 Agent 的桌面端和移动端回归测试。

验收重点：

- 用户可以不理解 Task/Run 就完成一次正常 Agent 工作；
- 用户可以把一次对话结果转入正式项目；
- 页面不伪造在线、执行中、流式、思考或已完成状态。

### 阶段 2：多 Agent 协作主线

目标：让多 Agent 协作从“领域对象存在”变成“用户看得见、能操作、能验证”。

主要工作：

- 设计项目级 Agent 团队视图；
- 展示每个 Agent 的身份、能力、在线状态、当前任务和负载；
- 展示任务的并行、依赖、阻塞、执行、失败和重试；
- 将成果物、交接包、下游任务和审核门禁串成一条可读路径；
- 在工作区中突出“谁正在做什么、谁等待什么、下一步交给谁”；
- 为接力式协作和分发式协作分别提供清晰视图；
- 为交接规范提供固定字段和用户可读摘要；
- 提供“任务完成但成果未入库”等中间异常状态。

必须有一条真实端到端验收：

```text
Agent A 与 Agent B 并行执行
→ A 上传成果物和交接
→ B 读取批准输入继续执行
→ 一个任务失败并重试
→ 一个成果被退回并产生新版本
→ 复核 Agent 给出结论
→ 人工批准最终结果
```

验收重点：

- 至少两个 Agent 的分工和交接真实发生；
- 不依赖静态数据库剧本；
- 任务、Run、成果物、交接、证据和审核可以互相追溯；
- 失败、重试、退回和阻塞状态不会被隐藏；
- 工作区一眼能看出多 Agent 协作，而不是单一聊天。

### 阶段 3：通用垂直工作流包

目标：把数学建模从特殊页面提升为通用工作流包体系的首个实例。

主要工作：

- 抽象 Workflow、WorkflowVersion、Stage、Node、Role、HandoffContract、GatePolicy、DeliveryAdapter 等概念；
- 将 CUMCM 模板映射到通用工作流定义；
- 将长文写作作为第二个工作流包；
- 统一任务 DAG、角色、提示词、成果物和审核配置；
- 明确工作流的输入、输出、依赖、并行、重试和人工介入；
- 将论文交付、文档导出等差异放到交付适配器；
- 在工作流包页面清楚标注“生成骨架、待执行、待审核、可交付”等状态。

验收重点：

- 数学建模和文档写作可以共享同一套平台内核；
- 更换工作流包不需要重写 Task/Run/Artifact/Handoff/Review；
- 一个工作流实例可以完整解释每个 Agent 为什么执行、输入来自哪里、输出交给谁；
- 工作流版本变更不会改写历史项目。

### 阶段 4：自定义自动化编排

目标：允许用户创建自己的生产模板。

主要工作：

- 提供模板编辑器或结构化配置入口；
- 支持节点目标、提示词、角色、工具、输入输出和交接规范；
- 支持串行、并行、条件分支和人工确认；
- 支持失败重试、超时、预算和升级处理；
- 支持模板预览、校验、版本发布和复制；
- 支持从一次成功项目反向保存为模板；
- 为模板提供运行预览和测试项目。

验收重点：

- 用户无需改代码即可创建一条简单自动化流程；
- 模板能产生真实任务和交接，而不是只保存一段提示词；
- 模板运行失败时可以定位到具体节点和输入输出；
- 历史运行绑定原模板版本。

### 暂缓项：Git 产品能力

本阶段不把 GitHub 导入、平台仓库、PR、分支、推送和拉取纳入实施计划。GitHub 继续承担仓库托管和代码协作，synapforge 聚焦 Agent 协作生产和工作流自动化。

## 7. 当前不应做的事情

- 不把数学建模继续扩大成平台唯一产品叙事；
- 不把工作区继续做成单纯聊天产品；
- 不把多个 Agent 仅做成多个下拉选项；
- 不用静态演示数据冒充多 Agent 协作闭环；
- 不把“任务成功”直接等同于“成果物已批准”；
- 不把“模板已应用”描述成“最终结果已生成”；
- 不把自动派发描述成完全自动完成；
- 不新增第二套权限、审批或思考协议；
- 不为复制 GitHub 能力而开发平台 Git 仓库和 PR 系统；
- 不删除旧路由，不破坏已有 Agent Protocol、Gateway 和文件管理边界；
- 不把未完成的功能写成已经上线的产品承诺。

## 8. 产品成功标准

后续每一期实施都应回答四个问题：

1. 用户能否不用阅读内部实现就完成目标？
2. 多 Agent 的分工、交接和协作结果是否可见、可追溯、可复核？
3. 自动化工作流是否真的推进了任务，而不是只生成了静态页面或提示词？
4. 失败、阻塞、权限、上传、审核和交付状态是否如实呈现？

最终产品应让用户形成以下直觉：

```text
我可以先单独使用一个 Agent。
需要多人或多个 Agent 时，我可以把工作组织成项目。
流程稳定后，我可以把它保存成工作流反复运行。
平台负责协作、过程和交付记录；GitHub 继续负责 GitHub 的事情。
```
