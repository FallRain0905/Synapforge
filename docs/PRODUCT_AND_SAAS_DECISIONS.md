# 数学建模多 Agent 协作平台：产品与 SaaS 架构决策

> 文档状态：规划基线
>
> 文档目的：记录目前已经明确的产品方向、尚待确认的关键细节、SaaS 架构设计、Agent 接入边界，以及值得借鉴的商业 SaaS 和开源项目。
>
> 适用范围：数学建模竞赛是首个领域模板，但平台目标不是只服务数学建模，而是服务可以拆解、交接、复核、生成和交付的复杂知识工作。

## 1. 结论摘要

这个平台的核心价值不是“让多个 Agent 同时聊天”，而是把复杂任务变成一条可追踪、可复现、可审核、可交付的生产流程：

```text
任务拆解
  -> 分配或认领
  -> Agent 执行
  -> 结构化交接
  -> 成果物版本化
  -> 证据和运行记录绑定
  -> 独立复核与人工门禁
  -> 文档、PPT、图表或代码交付
```

平台应当同时满足两类协作：

1. **接力式协作**：A Agent 完成阶段性工作，提交交接包；B Agent 获取上下文后继续推进，再交给 C Agent。
2. **分发式协作**：主控 Agent 或项目负责人拆分任务，并行派发给多个 Agent，接收成果后汇总、比较和复核。

最终产品可以概括为：

> **面向复杂知识工作的多 Agent 工作流 SaaS，数学建模是第一套高价值领域模板。**

平台最重要的资产不是某个模型，而是结构化任务、成果物版本、证据关系、执行记录、审核门禁和可复用模板形成的项目过程数据。

## 2. 产品定位与边界

### 2.1 产品解决的问题

普通聊天式 Agent 在多人或多 Agent 协作时容易出现以下问题：

- 后续 Agent 不知道前一个 Agent 做了什么、为什么这样做、哪些结论已经验证。
- 关键信息存在于聊天上下文中，无法稳定复用、搜索或交接。
- 文件有多个版本，但没有明确的输入、输出、来源和批准关系。
- 代码可以运行，但运行环境、参数、随机种子和数据版本没有被记录。
- Agent 使用了当时不应获得的未来信息，事后却很难发现。
- 任务可以被重复执行、越权执行或绕过审核，最终交付无法证明过程可靠。
- 报告、论文、PPT、图表和代码彼此脱节，修改一个结论后无法知道哪些产物需要重新生成。

平台针对的是上述过程性问题，而不是单纯提高某个模型的回答质量。

### 2.2 首要用户

首批用户可以按优先级分为：

| 用户 | 主要需求 | 平台价值 |
| --- | --- | --- |
| 数学建模竞赛队伍 | 题目分析、分题、建模、编程、复核、论文交付 | 提供完整的竞赛工作流与模板 |
| 复杂课题小组 | 资料分析、实验、报告与答辩材料 | 提供任务交接与证据追溯 |
| 研究团队 | 数据、代码、实验和论文的协作 | 提供可复现运行与审计 |
| 企业分析团队 | 多角色研究、审批和材料生产 | 提供权限、门禁、版本和交付流程 |

### 2.3 非目标

以下内容不应成为第一阶段的核心：

- 公开的 Agent 社交网络或 Agent 排行榜。
- 只追求“最多 Agent 同时对话”的聊天产品。
- 一开始就建设复杂计费、公开 Agent 市场和大规模插件生态。
- 取代队员、研究员或负责人对模型假设、结果和最终论文的判断。
- 把所有代码、论文和文档都强制迁移到平台内部编辑器。

平台可以保留自由讨论，但正式工作必须沉淀为任务、交接、成果物、运行记录或审核结果。

## 3. 已经明确的产品决策

下表中的内容可以作为当前架构基线；后续如果修改，需要记录决策原因和迁移影响。

| 领域 | 当前决定 | 原因 |
| --- | --- | --- |
| 产品范围 | 通用复杂知识工作平台，数学建模为首个领域包 | 避免产品被单一竞赛周期限制 |
| 核心对象 | Task、Handoff、Artifact、Run、Evidence、Review、Gate、Event | 让过程可以被复用、审计和恢复 |
| 协作方式 | 同时支持接力式与分发式协作 | 覆盖串行研究和并行研究两种真实工作流 |
| 部署形态 | 云端控制平面与资料存储，本地 Agent 执行 | 兼顾统一协作、隐私、代码执行和本地模型 |
| Agent 连接 | MCP 加平台 Gateway、relay-agent、Adapter 和自有协议 | MCP 负责能力调用，不足以单独承担任务状态和审计 |
| 网络方式 | 本地 Agent 主动外连，不要求队员电脑开放公网端口 | 降低部署和安全风险 |
| 版本管理 | Git 管代码和 LaTeX，平台管成果物索引、证据关系与审批状态 | 利用成熟工具，同时补齐知识工作审计能力 |
| 模型来源 | BYOK、云端模型、本地模型并存 | 兼顾成本、隐私、性能和可控性 |
| 执行支持 | Python 首个完整执行栈，R、MATLAB、Julia 通过 Runner 扩展 | 先覆盖建模高频需求，保留跨语言接口 |
| 通信方式 | 普通聊天为辅助；正式交接必须结构化 | 防止关键上下文只存在于聊天记录中 |
| 权限模型 | 多组织、多队伍、多项目隔离；Agent 不得伪装成人员审批 | 满足 SaaS 租户隔离与责任边界 |
| 审核方式 | 机器审计、独立 Agent 复核、人工门禁分级组合 | 同时覆盖确定性错误和语义性错误 |
| 模板策略 | 通用平台内核加 CUMCM 首套赛事模板 | 领域模板带来落地速度，内核保持可扩展 |
| 建设策略 | 分阶段实施，但从完整目标架构和协议出发 | 避免先做孤立 Demo 后整体推倒重来 |

## 4. 平台的真正使用意义

用户使用平台，不是为了把 Agent 换成另一个聊天入口，而是为了获得五种单独使用 Agent 很难获得的能力。

### 4.1 把工作变成可接力的过程

每个 Agent 不需要携带全部历史聊天上下文，只需要接收：

- 当前任务目标和完成标准。
- 已批准的输入成果物。
- 前置 Agent 的结构化交接。
- 必须遵守的假设、约束和信息边界。
- 需要产出的成果物类型。
- 任务状态和剩余风险。

这样可以降低上下文长度，也让不同厂商、不同模型、不同本地电脑上的 Agent 能够接力。

### 4.2 把并行工作变成可汇总的结果

主控 Agent 或项目负责人可以把一个大任务拆成多个子任务，例如：

- Agent B 负责数据画像。
- Agent C 负责模型候选方案。
- Agent D 负责文献和方法核查。
- Agent E 负责代码实验。

平台收集各个结果，并通过成果物类型、输入输出关系和审核状态组织汇总，而不是把四段聊天直接拼在一起。

### 4.3 把“结论”绑定到证据

一个正式结论必须能够回溯到：

```text
结论
  -> 图表或结果表
  -> 运行记录
  -> 代码版本
  -> 输入数据版本
  -> 执行环境和参数
  -> 审核意见与批准记录
```

这对数学建模尤其重要，因为数值结果、代码、论文表述和模型假设必须一致。

### 4.4 把不可实施的事后信息暴露出来

任务和数据集必须声明可访问时间点。平台记录 Agent 实际读取了哪些数据，从而审计：

- 是否把未来真实数据送入过去时点不可获得的优化过程。
- 是否混用了预测值、计划值和真实执行值。
- 是否用复盘阶段的信息修改执行阶段结论。
- 论文是否引用了未经过批准的运行结果。

这是一项区别于普通项目管理软件的领域能力。

### 4.5 把复杂材料生产变成模板化流水线

同一个项目可以根据已批准的成果物生成：

- 建模分析报告。
- 研究报告或技术报告。
- 论文正文和附录。
- PPT 或答辩演示文稿。
- 结果表、统计图、流程图和示意图。
- 代码包、运行清单和最终提交包。

模板只负责结构、样式和装配；结论必须来自经过审核的成果物和证据。

## 5. 核心使用场景

### 5.1 接力式协作

典型流程：

1. 项目负责人创建“问题一建模”任务，指定输入是题面和事实台账，输出是模型分析包。
2. Agent A 领取任务，分析题面，生成变量、假设、候选模型和风险清单。
3. Agent A 提交 `PASS_WITH_ASSUMPTIONS` 交接包，并关联 `problem_analysis` 和 `model_spec` 两个成果物。
4. Agent B 接收交接，先查看前置产物和未解决问题，再完成代码实现或参数估计。
5. Agent B 上传代码、运行清单和结果表，提交给独立 Agent C 复核。
6. C 通过审核后，结果才有资格被论文任务引用。

关键点：B 接收的是经过结构化整理的任务上下文，而不是 A 的全部聊天记录。

### 5.2 分发式协作

典型流程：

1. 主控 Agent 将“完整问题”拆分成数据、建模、代码、图表和文献核验等子任务。
2. 平台根据能力声明、权限、负载和截止时间推荐执行 Agent。
3. B、C、D 并行领取任务，分别产出成果物。
4. 平台自动检查输入是否齐全、结果是否重复、文件是否有哈希和运行记录。
5. 汇总 Agent 读取多个已完成产物，生成综合结果和冲突清单。
6. 人员或独立 Agent 处理冲突，最终通过阶段门禁。

关键点：并行不是把任务简单广播出去，而是要有依赖、租约、去重、汇总和冲突处理机制。

### 5.3 多 Agent 独立复核

复核 Agent 不应只重复原 Agent 的提示词，而应接收受控的审查输入：

- 原模型和假设。
- 代码和运行记录。
- 结果表和图表。
- 题目原文及事实台账。

复核输出包括问题等级、证据定位、重现步骤、修正建议和是否阻断下游。平台可要求复核 Agent 与原执行 Agent 使用不同模型或不同提示策略。

### 5.4 人机协作与人工审批

平台应允许人直接修改任务、成果物和交接状态，但要区分：

- 人员提出意见。
- Agent 执行修改。
- 人员批准正式结果。

Agent 可以建议批准，不能伪造人员批准。人工门禁默认用于题面事实定稿、模型假设定稿、正式结果发布、论文生成和最终交付包导出。

### 5.5 报告、论文、PPT 和图表装配

生成任务应引用已经批准的素材，而不是直接从长聊天中生成最终文档。生成链路包括：

```text
已批准结论与数据
  -> 内容大纲
  -> 文档或幻灯片素材
  -> 图表和公式
  -> 编译/渲染
  -> 格式审计
  -> 人工确认
```

一个图表应记录数据来源、生成脚本、参数、输出文件哈希和被哪些段落引用。

### 5.6 模板化重复生产

赛事包、项目包和组织模板应能够复用：

- 任务 DAG。
- 交接字段。
- 成果物类型和命名规则。
- 检查器。
- 报告和 PPT 模板。
- 阶段门禁。

例如，CUMCM 模板可以预置四问分析、代码目录、结果审计和论文检查；换成企业研究报告时，只替换模板包，不重写平台内核。

## 6. 总体 SaaS 架构

### 6.1 分层结构

```text
┌─────────────────────────────────────────────────────────┐
│ Web / Desktop UI                                        │
│ 项目总览、任务看板、交接中心、成果物、运行、审核、交付     │
└───────────────────────┬─────────────────────────────────┘
                        │ HTTPS / WebSocket / SSE
┌───────────────────────▼─────────────────────────────────┐
│ Platform Control Plane                                  │
│ Auth │ Tenant │ Project │ Task │ Handoff │ Artifact     │
│ Run │ Evidence │ Review │ Gate │ Template │ Audit      │
└─────────────┬───────────────────┬──────────────────────┘
              │                   │
       ┌──────▼──────┐     ┌──────▼──────────────────────┐
       │ Data Plane   │     │ Integration / Event Plane    │
       │ PostgreSQL   │     │ Agent Gateway               │
       │ S3 Object    │     │ NATS / Webhooks / MCP       │
       │ Git          │     │ Model Gateway / Providers   │
       └──────────────┘     └─────────────┬───────────────┘
                                         │ outbound only
                              ┌──────────▼───────────┐
                              │ Personal Agent Host   │
                              │ agentd / Adapter      │
                              │ Runner / Local Model  │
                              │ Workspace / Approval  │
                              └───────────────────────┘
```

### 6.2 控制平面

控制平面是平台必须掌握的事实来源，负责：

- 组织、队伍、项目和成员身份。
- 项目模板、阶段和任务状态机。
- 任务依赖、认领、租约、重试和取消。
- 结构化交接、成果物注册和审核状态。
- 权限检查、数据访问策略和信息边界。
- 运行记录、事件日志和成本统计。
- 通知、待办和阶段门禁。

控制平面不应把关键状态交给某个 Agent 的上下文或某个聊天服务保存。

### 6.3 数据平面

| 数据类型 | 推荐存储 | 平台职责 |
| --- | --- | --- |
| 组织、任务、状态、权限、事件索引 | PostgreSQL | 事务、一致性、租户隔离和查询 |
| 原始文件、数据集、运行输出、编译 PDF | S3 兼容对象存储 | 内容哈希、分块上传、生命周期和下载授权 |
| 代码、LaTeX、配置 | Git | 分支、提交、Diff 和合并 |
| 文档协同状态 | Yjs/Hocuspocus 存储层 | 实时同步、快照和冲突处理 |
| 搜索索引 | PostgreSQL FTS 或独立搜索引擎 | 按项目、成果物、结论和事件检索 |
| 事件和异步任务 | NATS JetStream 或同类事件系统 | 投递、重试、顺序和幂等 |

Git 与平台不是互相替代关系。Git 记录源代码和论文源文件的修改历史，平台记录这些版本在什么任务中产生、是否批准、被什么结论引用。

### 6.4 执行平面

本地 Agent 主动与 Gateway 建立 HTTPS/WebSocket 连接，执行平台下发的授权任务：

- 同步授权工作区。
- 拉取任务和交接包。
- 调用本地模型或远程模型。
- 执行 Python、R、MATLAB、Julia 等代码。
- 记录输入、参数、环境和输出。
- 上传成果物与运行结果。
- 断线后通过事件序号和幂等键恢复。

本地执行平面不直接决定任务是否通过门禁；它只提交执行结果和建议状态。

### 6.5 集成平面

集成平面把外部 Agent、模型服务、代码托管、对象存储和文档工具连接起来。平台需要维护稳定的内部协议，外部工具变化只影响适配器。

## 7. 多租户、组织和权限设计

### 7.1 层级关系

```text
Organization
  ├─ Team
  │   ├─ HumanMember
  │   ├─ Agent
  │   └─ Project
  ├─ SharedTemplate
  └─ Policy
```

一个成员可以加入多个队伍；一个 Agent 归属于一个成员，但可以被授权加入多个项目。项目是资料、任务、运行和审核的主要隔离边界。

### 7.2 最小角色集合

| 角色 | 权限重点 |
| --- | --- |
| Organization Owner | 组织设置、成员、配额、策略 |
| Team Admin | 队伍成员、项目和模板管理 |
| Project Lead | 项目任务、阶段、门禁和最终交付 |
| Contributor | 执行授权任务、提交成果物和交接 |
| Reviewer | 查看指定范围、提交复核意见、不能替代人工批准 |
| Agent | 按授权执行和回传，不能自行扩大权限 |
| Observer | 只读项目进度和公开成果物 |

### 7.3 权限原则

- 默认拒绝跨项目读取。
- 成果物下载必须经过项目权限和数据策略检查。
- Agent 权限不自动继承其所有者的全部人类权限，需显式授予项目范围。
- 正式批准必须绑定真实成员身份、时间和审计事件。
- 任何跨组织共享都要有明确的共享对象、有效期和撤销机制。
- 访问原始数据、执行代码和导出最终包可以使用不同权限。

首期可以使用 RBAC；当项目、数据集和成果物权限变复杂时，再增加 ABAC 条件，例如“只允许在截止时间前读取预测数据”。

## 8. Agent 接入设计

### 8.1 为什么不能只使用 MCP

MCP 很适合描述工具、资源和提示，让 Agent 能够调用平台能力，例如读取任务、创建成果物或请求运行。但 MCP 本身不完整解决：

- 长时间任务的租约和状态恢复。
- 多 Agent 的任务分派和竞争认领。
- 可靠消息投递和重复消费。
- 审批、门禁和不可抵赖的人员身份。
- 运行环境、文件哈希和证据链。
- 断线重连、取消、重试和配额。

因此推荐采用：

```text
外部 Agent
  -> Adapter / MCP Client
  -> agentd 或 relay-agent
  -> Agent Gateway
  -> 平台任务、成果物、交接和审计协议
```

MCP 是连接层的一部分，不是整个平台的状态数据库和工作流协议。

### 8.2 四个连接组件的职责

| 组件 | 所在位置 | 职责 |
| --- | --- | --- |
| Agent Gateway | 云端 | 认证设备、下发任务、接收心跳和结果、执行策略 |
| relay-agent | 云端或受控中转环境 | 在平台与外部 Agent 之间转发消息、管理会话、处理重连 |
| agentd | 用户本地电脑 | 访问本地工作区、执行任务、控制本地模型和 Runner |
| Adapter | 本地或云端 | 将 Codex、Claude Code、Harness、Zcode 等工具的接口映射到平台协议 |

### 8.3 主流 Agent 的接入方式

| 外部 Agent 类型 | 首选接入 | 备用接入 | 审计能力 |
| --- | --- | --- | --- |
| 支持 MCP 的 Agent | 平台 MCP Server 暴露任务、成果物和交接工具 | SDK 调用平台 API | 高 |
| 支持 CLI 或 Hook 的编码 Agent | agentd 启动 Adapter，使用工作区和任务上下文 | 命令行包装器 | 中高 |
| 支持 API/Headless 的 Agent | Provider Adapter 或平台统一 Agent API | relay-agent 转发 | 高 |
| 只能交互式运行的桌面 Agent | 本地桌面连接器或人工导入导出 | 手动上传交接包 | 中低 |

对 Codex、Claude Code、各类 Harness、Zcode 等，不应假定它们具备完全相同的生命周期接口。平台内部统一抽象为：

```text
claim_task
prepare_context
start_run
emit_progress
submit_artifacts
create_handoff
request_review
cancel_or_resume
```

各工具只需要由 Adapter 实现这些动作。工具升级时，优先更新 Adapter，不修改 Task、Handoff 和 Artifact 的核心协议。

### 8.4 连接与安全

本地 Agent 的推荐连接流程：

1. 用户在平台创建设备配对码或一次性注册链接。
2. 本地 `agentd` 使用短期凭证注册，并生成长期设备密钥。
3. Gateway 为设备签发项目范围和能力范围的令牌。
4. Agent 通过主动外连保持心跳，不暴露入站公网端口。
5. 任务下发附带幂等键、过期时间、允许的输入成果物和执行策略。
6. 结果上传后由平台校验哈希、权限、任务状态和运行清单。
7. 本地确认窗口处理危险命令、外部网络访问和敏感文件上传。

## 9. 核心领域对象与协议

### 9.1 Task

任务是可执行、可审核和可追踪的最小工作单元。至少需要：

```text
task_id
project_id
parent_task_id
title
objective
acceptance_criteria
status
priority
assignee_type
assignee_id
input_artifact_ids
required_output_types
required_capabilities
dependency_task_ids
deadline
information_boundary
resource_policy
requires_human_approval
created_by
created_at
updated_at
```

建议状态：

```text
DRAFT -> READY -> CLAIMED -> RUNNING -> WAITING_REVIEW -> APPROVED
```

异常状态：

```text
BLOCKED / NEEDS_REVISION / FAILED / CANCELLED
```

状态变化必须经过服务端校验，不能由客户端任意写入 `APPROVED`。

### 9.2 Handoff

交接包是接力式协作的核心协议，也是分发式汇总的标准输入。建议沿用以下结构：

```json
{
  "handoff_id": "handoff_01",
  "project_id": "project_01",
  "task_id": "task_01",
  "sender_agent_id": "agent_a",
  "receiver": {"type": "agent", "id": "agent_b"},
  "status": "PASS_WITH_ASSUMPTIONS",
  "objective": "完成问题一的模型分析并交给代码 Agent",
  "completed": [],
  "input_artifacts": [],
  "output_artifacts": [],
  "key_conclusions": [],
  "assumptions": [],
  "evidence_refs": [],
  "open_questions": [],
  "risks": [],
  "next_actions": [],
  "requires_human_approval": true,
  "schema_version": "1.0"
}
```

交接状态：

```text
PASS / PASS_WITH_ASSUMPTIONS / NEEDS_REVISION / BLOCKED
```

风险和问题至少区分：

```text
fatal / major / minor
```

### 9.3 Artifact

成果物包括文档、代码、数据、结果、图表、报告和提交包。每个版本至少保存：

- 唯一 ID、版本号和内容哈希。
- 创建者、执行 Agent 和创建时间。
- 输入成果物、关联任务和运行记录。
- Git commit 或文档快照。
- 审核状态、适用范围和是否允许下游引用。
- 引用与被引用关系。
- 未解决问题、风险和数据边界。

建议首批类型：

```text
problem_source
problem_facts
problem_analysis
data_profile
model_spec
code
experiment_plan
run_manifest
result_table
figure
audit_report
review_report
paper_source
compiled_pdf
submission_bundle
```

### 9.4 Run Manifest

任何可以影响正式结论的执行都应生成运行清单：

```text
run_id
task_id
source_commit
input_artifact_hashes
environment_image_digest
dependency_lock
parameters
random_seed
model_provider
model_name
tool_versions
information_boundary_snapshot
actual_read_files
start_time
end_time
stdout
stderr
exit_code
output_artifact_hashes
```

运行清单的目标不是记录所有调试细节，而是使另一台机器能够判断“这次结果是否可重现、是否合法、是否应被引用”。

### 9.5 Evidence 和 Review

`Evidence` 连接结论与支撑材料，例如：

```text
Conclusion -> ResultTable -> Run -> CodeCommit -> InputArtifact
Conclusion -> Figure -> PlotScript -> DatasetVersion
```

`Review` 记录审查者、审查范围、问题等级、证据位置、修复建议、结论和时间。`Gate` 只根据已登记的审核结果、风险清单和必要人工批准放行。

## 10. 任务状态、事件与可靠性

### 10.1 事件来源

所有重要操作产生不可变事件，例如：

```text
project.created
task.created
task.claimed
task.started
task.blocked
task.submitted
handoff.created
handoff.accepted
artifact.registered
artifact.approved
run.started
run.completed
review.created
gate.passed
gate.rejected
export.created
```

事件至少带有：事件 ID、租户和项目 ID、发生者、发生时间、事件类型、对象 ID、幂等键和载荷版本。

### 10.2 幂等和重试

- 客户端每次提交携带幂等键。
- 服务端对同一项目和操作类型约束重复写入。
- 事件投递失败可以重试，但消费者必须幂等。
- 运行任务的重试要区分“重新执行”和“重新上传结果”。
- 取消任务要留下取消原因和执行方，不能删除历史运行记录。

### 10.3 离线恢复

Agent 断线时：

- 当前运行保留本地运行 ID 和输出缓存。
- Gateway 保存最后确认的事件序号。
- 恢复连接后按序补发事件。
- 平台根据幂等键去重。
- 如果任务租约已过期，平台先进入冲突处理，不自动覆盖其他 Agent 的新结果。

## 11. SaaS 产品机制借鉴

平台应学习成熟 SaaS 的机制，但不直接复制其全部产品形态。

| 借鉴对象 | 借鉴内容 | 在本平台中的转化 | 不应直接照搬 |
| --- | --- | --- | --- |
| Linear / Asana | 任务、负责人、依赖、视图、状态和通知 | 任务 DAG、阶段看板、租约、截止时间 | 纯人工任务管理，不足以表达运行和证据 |
| Notion / Coda | 页面、数据库、模板、关联和知识空间 | 成果物浏览器、模板包、结构化项目知识 | 让自由页面成为唯一事实来源 |
| GitHub / GitLab | 分支、提交、Review、CI、制品和权限 | 代码与论文源文件版本，运行与审核联动 | 把非代码成果物全部当 Git 文件管理 |
| Google Docs | 实时协同、评论、建议和版本 | 分析报告、论文素材和多人审阅 | 让实时编辑绕过正式版本和门禁 |
| Figma | 多人实时编辑、评论、版本和分享 | 图表、PPT 素材和视觉产物协作 | 复杂研究逻辑不适合只用画布表达 |
| Slack / Teams | 频道、线程、通知和集成 | 辅助讨论、事件通知和待办提醒 | 用聊天记录代替交接包和任务状态 |
| Dropbox / Drive | 文件同步、分享、回收和权限 | 原始资料、快照、下载授权和归档 | 没有来源关系的“文件堆” |
| Zapier / n8n | 触发器、动作、连接器 | 非核心通知和外围自动化 | 把核心任务状态放到不可审计的自动化脚本里 |
| Datadog / Sentry | 日志、指标、追踪和告警 | Agent 在线状态、运行失败、延迟和成本 | 只看系统指标而忽略研究结果质量 |

### 11.1 平台的差异化组合

可以把产品理解为以下组合，但其核心对象必须由本平台统一管理：

```text
Linear 的任务流
+ Notion 的知识空间
+ GitLab 的代码审查
+ Google Docs 的实时协同
+ Temporal 的可靠工作流
+ MLflow/DVC 的实验追踪
+ Agent Gateway 的跨 Agent 接入
+ 数学建模领域模板和信息边界审计
```

真正的差异化来自最后三项，而不是界面上是否有看板或聊天。

## 12. 开源项目借鉴与边界

### 12.1 协议和 Agent 编排

| 项目或标准 | 用途 | 建议定位 |
| --- | --- | --- |
| MCP | Agent 调用工具、资源和提示 | 作为接入协议，不作为平台状态库 |
| A2A 或同类 Agent 通信规范 | Agent 间任务发现和消息表达 | 评估兼容，不直接替代平台交接协议 |
| LangGraph | 单个 Agent 或 Agent 团队内部有状态编排 | 可嵌入执行器，状态最终回写平台 |
| Temporal | 长流程、重试、超时、补偿和恢复 | 适合核心工作流编排 |
| AutoGen / CrewAI / AgentScope / MetaGPT | 角色协作、实验和提示模式 | 用于参考或作为可选运行时，不作为唯一事实来源 |

平台必须自研并固定：Task、Handoff、Artifact、Run、Evidence、Review、Gate 和 Event 的数据契约。

### 12.2 协同编辑与文档

- `Yjs`：实时协同的数据同步层。
- `Tiptap`：结构化富文本编辑器。
- `Hocuspocus`：Yjs 的服务端协同基础设施。
- Markdown、LaTeX、Quarto、Typst、Pandoc：适合可版本化的研究源文件和文档生成。
- Marp、Slidev、PptxGenJS：适合文本或代码驱动的 PPT 生成。

建议把实时编辑层和正式成果物层分开：编辑过程可以频繁产生临时版本，只有被提交并登记的快照才进入正式证据链。

### 12.3 数据、实验与血缘

- `PostgreSQL`：结构化事务和权限事实来源。
- S3 兼容对象存储：文件、数据和输出。
- Git：代码和论文源文件。
- `MLflow`：实验参数、指标和模型运行记录，可作为实验服务参考。
- `DVC`、`lakeFS`：数据版本和大文件版本管理，可按需求引入。
- `OpenLineage`：数据和任务血缘表达，可与平台 Evidence 图谱对接。

首期不建议同时引入所有数据平台组件。平台应先建立自己的简洁 Artifact/Evidence 契约，再通过适配器对接这些项目。

### 12.4 执行、身份和观测

- Docker/Podman：隔离 Python 运行环境。
- Keycloak 或 Ory：OIDC、组织身份和企业 SSO 的基础能力。
- OpenTelemetry：服务、Agent 和 Runner 的统一追踪。
- Prometheus/Grafana：指标和系统看板。
- Langfuse 或同类系统：模型调用追踪、Token、费用和延迟。
- LiteLLM 或 OpenAI-compatible Adapter：统一云模型、本地模型和 BYOK。

这些组件可以复用基础能力，但平台仍需要额外记录“这次模型调用服务于哪个任务、产生了哪个成果物、是否被批准引用”。

## 13. 模板包设计

### 13.1 模板包的组成

一个领域模板包不应只是几份提示词，而应包含：

```text
template.yaml
  ├─ stages
  ├─ task_templates
  ├─ handoff_schema_extensions
  ├─ artifact_types
  ├─ validators
  ├─ review_checklists
  ├─ document_templates
  ├─ runner_profiles
  └─ export_profiles
```

每个模板包需要声明版本、适用赛事或组织、输入格式、输出格式、检查器版本和升级兼容策略。

### 13.2 CUMCM 首套模板

建议兼容已有目录和文件：

```text
PROBLEM_ANALYSIS.md
PROBLEM_FACTS.json
DATA_PROFILE.json
MODELING_REPORT.md
RESULTS.md
AUDIT_REPORT.md
COMP_REVIEW.md
code/
figures/
output/
paper/
```

导入适配器应保留：

- 原始文件路径。
- 文件内容哈希。
- 目录层级。
- 产生时间和导入时间。
- 文件与任务、成果物和证据关系的推断结果。
- 无法自动判断的字段和待人工确认项。

### 13.3 后续模板方向

在平台内核稳定后，可以增加：

- 研究课题与论文模板。
- 技术方案与可行性报告模板。
- 企业数据分析报告模板。
- 答辩 PPT 与演示模板。
- 调研、访谈和市场分析模板。
- 代码项目、测试报告和发布包模板。

模板市场属于后续能力；首期更重要的是模板包版本可控、输出可审计和升级不会破坏已有项目。

## 14. 关键产品模块

### 14.1 项目总览

显示阶段进度、关键风险、待审核事项、Agent 在线状态、最近事件和截止时间。它是负责人判断项目健康度的工作台，不是营销首页。

### 14.2 任务看板与 DAG

支持列表、看板和依赖图视图。必须展示：负责人、输入、输出、阻塞原因、重试次数、租约和门禁状态。

### 14.3 交接中心

分为待接收、进行中、待审核、需返工和已归档。交接包应能一键打开相关任务、成果物、运行和风险。

### 14.4 成果物浏览器

提供文件树、版本、Diff、来源链、被引用位置、审批状态和下载授权。用户查看的重点不是“某个文件在哪”，而是“这个结论来自什么”。

### 14.5 运行控制台

展示参数、代码版本、环境、输入、日志、输出、随机种子、失败原因和复现操作。运行结果不能脱离 Run Manifest 单独标记为正式结果。

### 14.6 审核中心

同时呈现机器审计、独立 Agent 复核和人工审批。问题按 `fatal`、`major`、`minor` 分级；`fatal` 自动阻断下游，其他问题必须进入风险清单。

### 14.7 证据图谱

以图或可展开链路展示结论、数据、代码、运行、图表、报告段落和审批之间的关系。首期可以先用关系表和链路面板实现，不必一开始建设复杂图数据库。

### 14.8 论文与交付中心

支持 LaTeX/Word 编译、页数、匿名、格式、图表引用、附件完整性、压缩包生成和版本冻结。

## 15. 待明确事项

下面的事项按优先级划分。P0 事项不明确时，容易导致协议和数据库返工；P1 事项可以在核心契约确定后逐步落地；P2 事项不影响首个可用领域版本。

### 15.1 P0：必须优先拍板

| 事项 | 需要明确的问题 | 当前建议 | 未决影响 |
| --- | --- | --- | --- |
| 首批用户 | 是竞赛队伍、课题组还是企业团队优先 | 先以 3 人数学建模队伍为设计基准，同时保留通用命名 | 影响模板、权限和获客 |
| 首个正式场景 | 先做接力、分发还是完整四问流程 | 同时定义两者，但先用接力加独立复核验证协议 | 影响任务和交接 API |
| 单项目规模 | Agent 数、任务数、文件大小和并发运行量 | 先按 3 至 10 人、10 至 50 个 Agent、数百任务设计 | 影响队列、存储和成本 |
| 身份方式 | 个人账号、组织邀请、OIDC 或学校账号 | 首期邮箱/设备配对，结构上兼容 OIDC | 影响多租户和登录设计 |
| 默认数据级别 | 项目是否默认私有，模型是否可外发 | 默认私有，云端模型外发需项目策略允许 | 影响模型 Gateway 和日志 |
| 任务状态机 | 哪些状态可跳转、谁可修改 | 服务端固定状态机，模板允许增加业务状态但不能绕过门禁 | 影响所有客户端 |
| 正式成果物标准 | 哪些版本允许下游任务使用 | 只有已登记、哈希完整、输入明确且通过门禁的版本可作为正式输入 | 影响 Artifact 数据模型 |
| 人工门禁 | 哪些节点必须真人确认 | 事实、假设、正式结果、论文生成、最终导出默认需要人工确认 | 影响发布流程 |
| 信息边界 | 如何声明和校验可用数据 | 为数据集记录可访问时间、观测/预测/计划/真实标签和读取清单 | 影响 Runner 与审计 |
| Agent 身份 | Agent 是否代表成员，是否允许自注册 | Agent 是成员名下设备，需配对和显式授权 | 影响安全模型 |
| 可信事实来源 | 平台、Git 还是外部文档为准 | Task/Artifact/Review/Gate 以平台为准，代码/LaTeX 源以 Git 为准 | 影响同步和冲突处理 |

### 15.2 P1：核心契约后确认

| 事项 | 需要明确的问题 | 推荐初始方案 |
| --- | --- | --- |
| 云供应商 | 是否优先国内云、国际云或自托管 | 采用 PostgreSQL + S3 兼容接口，避免绑定供应商 |
| 对象存储 | 是否需要大文件、分块和版本保留 | 支持分块、断点续传、内容哈希和生命周期策略 |
| 事件系统 | 是否一开始使用 NATS 或只用数据库队列 | 先用事务事件表验证模型，达到异步需求后接 NATS JetStream |
| 工作流引擎 | Temporal 是否首期引入 | 长任务和补偿流程复杂时使用 Temporal；简单状态不强行套工作流 |
| 文档格式 | Markdown、Tiptap、LaTeX、Word 的优先顺序 | 分析用 Markdown/Tiptap，论文保留 LaTeX/Word 双轨 |
| PPT 格式 | 使用 Markdown 幻灯片还是 PPTX | 先支持可版本化的 Marp/Slidev，随后加入 PptxGenJS 导出 |
| 运行方式 | 本地运行、云端 Runner 或混合 | 本地 Runner 为主，云端隔离 Runner 可选 |
| 容器隔离 | Docker/Podman 的支持范围 | Python 先行，限制路径、网络、CPU、内存和时间 |
| 模型网关 | BYOK 和本地模型的配置范围 | 统一模型调用接口，项目级允许/禁止外发 |
| 配额 | Token、运行时、存储和并发限制 | 组织、队伍、项目三级配额，超限可排队或人工批准 |
| 日志策略 | 记录到什么粒度，是否保存完整提示词 | 默认记录调用元数据；完整内容受项目策略和敏感等级控制 |
| 搜索 | 是否使用独立搜索服务 | 首期 PostgreSQL FTS，数据规模增长后再拆服务 |
| 通知 | 邮件、站内、Webhook、飞书或 Teams | 站内通知和 Webhook 优先，第三方作为适配器 |
| 导入导出 | 如何保证跨部署恢复 | 项目导出包含 JSON manifest、对象文件、Git 引用和校验清单 |

### 15.3 P2：后续商业化与生态事项

| 事项 | 建议推迟到 |
| --- | --- |
| 订阅计费、按 Token/运行计费 | 有真实使用量和成本数据后 |
| 公开模板市场 | 模板包格式和升级机制稳定后 |
| 公开 Agent 市场 | Agent 权限、信誉和安全审核成熟后 |
| 企业 SSO、多地域部署 | 出现明确组织客户后 |
| 私有化安装包和 Helm/Kubernetes | 核心数据模型与备份恢复稳定后 |
| 跨组织成果物共享 | 权限、审计和撤销能力完成后 |
| 多语言界面 | 首批用户和模板验证后 |

## 16. 需要提前做出的架构选择

### 16.1 “平台事实”与“外部工具事实”分界

平台应负责：

- 任务是否可执行。
- 哪个 Agent 被授权执行。
- 哪些输入已批准。
- 哪个成果物可被下游引用。
- 哪次运行产生了哪个输出。
- 哪些风险阻断了门禁。
- 哪个成员完成了人工审批。

外部工具可以负责：

- 代码编辑和本地编译。
- 模型推理和工具调用。
- Git 分支和提交。
- 文档临时编辑。

如果外部工具出现故障，平台仍应保留任务和成果物状态；如果平台不可用，Agent 应能有限离线工作并在恢复后补传。

### 16.2 “实时协同”与“正式版本”分界

实时编辑适合思考和讨论，正式成果物适合审核和引用。建议使用三层版本：

1. 草稿状态：可快速变化，不可作为正式输入。
2. 提交版本：作者声明完成，等待机器或人工审查。
3. 批准版本：可被下游任务和文档生成引用。

### 16.3 “Agent 建议”与“平台决策”分界

Agent 可以提出：

- 任务拆分建议。
- 模型和工具建议。
- 风险和复核意见。
- 是否满足完成标准的判断。

平台根据权限、状态机和门禁规则决定：

- 是否允许执行。
- 是否允许写入成果物。
- 是否允许状态迁移。
- 是否允许下游引用。
- 是否允许最终导出。

## 17. 主要风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 范围过大 | 同时做聊天、编辑器、Agent 市场、计费和多赛事 | 先冻结核心协议和首个领域模板 |
| MCP 误用 | 把工具调用协议当成工作流和审计系统 | 自研平台任务、交接、成果物和事件协议 |
| 连接器脆弱 | 第三方 Agent 升级导致接入失效 | Adapter 隔离、契约测试、版本兼容矩阵 |
| 过度自动化 | Agent 自动批准或自动覆盖他人结果 | 服务端门禁和真人身份绑定 |
| 结果不可复现 | 环境、数据、参数和随机性遗漏 | Run Manifest、锁定依赖和环境摘要 |
| 信息泄漏 | 项目资料或未来数据被错误送出 | 项目级外发策略、读取清单和信息边界审计 |
| 协作噪声 | 聊天很多，正式产物很少 | 任务完成必须关联输出和交接 |
| 存储成本 | 大数据、日志和模型调用内容快速增长 | 分层存储、生命周期、脱敏和日志采样 |
| 权限复杂 | 成员、Agent、项目和成果物规则相互冲突 | 先 RBAC，条件权限保持明确扩展点 |
| 模板锁定 | CUMCM 特有字段侵入平台内核 | 模板包扩展 Schema，内核只保留通用对象 |
| 用户不愿迁移 | 已有 Git、网盘和聊天习惯 | 先做导入、索引和连接器，不强制迁移全部工具 |

## 18. 分阶段实施顺序

这里的“分阶段”是交付和验证顺序，不代表每个阶段都做成一次性临时架构。

### 阶段 0：领域契约和架构冻结

产出：

- 术语表、对象模型和 JSON Schema。
- Task、Handoff、Artifact、Run、Review、Gate、Event 状态机。
- 权限矩阵和信息边界策略。
- CUMCM 模板包规范。
- 外部 Agent Adapter 契约。
- 威胁模型、数据保留和导出恢复方案。

验收：用测试数据能完整描述一次接力任务和一次分发汇总，且不依赖具体前端或模型。

### 阶段 1：SaaS 基础控制平面

建设组织、队伍、项目、成员、登录、成果物登记、哈希、权限、事件时间线和基础导入导出。

验收：两个队伍互不可见；项目可以导入、浏览、下载、归档和恢复。

### 阶段 2：Agent Gateway 和本地 Agent

建设设备配对、心跳、任务拉取、结果回传、断线恢复、工作区同步、能力白名单和本地确认。

验收：两台不同电脑上的 Agent 加入同一项目，完成一次真实交接，重复回传不会产生重复成果物。

### 阶段 3：任务编排与交接中心

建设 DAG、任务租约、重试、取消、结构化交接、待审核和返工流程。

验收：不能绕过前置任务和审批；接力与分发两种流程都能完整跑通。

### 阶段 4：协同文档与 Git 集成

建设 Markdown/Tiptap 协同、评论、快照、Git 分支、Diff、提交和成果物索引。

验收：多人可协作完成分析报告，代码和论文修改能够追溯到成员、Agent、任务和提交。

### 阶段 5：运行、实验与审计

建设 Python Runner、运行 Manifest、参数和种子锁定、结果归档、约束审计、单位审计和信息边界审计。

验收：同一输入和环境可复现结果；读取未来数据的执行会被记录并按策略阻断。

### 阶段 6：CUMCM 领域模板

建设题目导入、四问任务编排、现有目录适配、问题事实台账、结果审计和论文检查。

验收：已有 CUMCM 项目可以无损或可解释地导入、继续执行并导出。

### 阶段 7：报告、论文、PPT 与交付

建设引用驱动的文档生成、图表清单、LaTeX/Word 编译、PPT 导出、格式审计和最终提交包冻结。

验收：每个关键结论均可追溯到批准的运行、代码和数据；最终包可在另一套部署中恢复。

### 阶段 8：稳定性、私有化与生态

建设备份恢复、多地域或私有部署、队伍配额、模板市场、更多赛事模板和企业身份集成。

## 19. 首批验收标准

首个完整验证不应只看页面是否能打开，而应验证一个端到端闭环：

1. 三名成员和至少三个 Agent 加入同一项目。
2. 一个任务被拆成两个并行子任务和一个汇总任务。
3. 另一个任务采用 A -> B -> C 接力方式完成。
4. Agent 使用不同接入方式，其中至少一个通过 MCP/Adapter，另一个通过本地 `agentd`。
5. 每个正式结果都有输入成果物、代码版本、运行清单和输出哈希。
6. 复核 Agent 能发现一个预置的重大问题，并阻断正式结果发布。
7. 人工修复并批准后，结果才可被报告或 PPT 生成任务引用。
8. 模拟断线、重复提交和任务取消，平台不丢失或重复确认任务。
9. 模拟读取不允许的数据，信息边界审计能够定位实际读取文件。
10. 导出项目后，在另一套部署或干净工作区中恢复任务、成果物、Git 引用和审核记录。

## 20. 推荐的默认答案

在尚未有真实用户反馈前，可以采用以下默认组合：

```text
前端：Next.js + React + TypeScript
协同编辑：Tiptap + Yjs + Hocuspocus
后端：FastAPI + Pydantic + SQLAlchemy
数据库：PostgreSQL
对象：S3 兼容存储
版本：Git，平台建立成果物索引
工作流：先用数据库状态机，长流程成熟后接 Temporal
事件：事务事件表起步，随后接 NATS JetStream
Agent：平台自有 Task/Handoff 协议 + MCP + agentd + Adapter
模型：统一 OpenAI-compatible Gateway，兼容 BYOK、Ollama、vLLM
执行：Docker/Podman Python Runner
身份：邮箱/邀请起步，OIDC/Keycloak 作为扩展
观测：OpenTelemetry + Prometheus/Grafana，模型追踪接 Langfuse
文档：Markdown/Tiptap、LaTeX/Word 双轨
PPT：Marp/Slidev 起步，PptxGenJS 扩展
部署：Docker Compose 起步，保留 Helm/Kubernetes 边界
```

这个组合的核心原则是：基础设施尽量复用成熟开源项目，任务、成果物、交接、证据和门禁保持平台自有且稳定。

## 21. 最终架构判断

项目最适合被设计成一套“可插拔的研究生产系统”：

- **SaaS 控制平面**负责组织、项目、任务、权限、成果物、事件和审核。
- **本地 Agent 平面**负责模型调用、代码执行、文件处理和本地隐私边界。
- **协议层**负责让 Codex、Claude Code、Harness、Zcode 以及后续工具以统一方式接入。
- **领域模板层**负责数学建模、论文、PPT、图表和其他复杂工作流的具体规则。
- **证据与审计层**负责让每个重要结论都能被复核和重现。

因此，平台的产品公式不是“多个 Agent + 聊天”，而是：

```text
可拆解任务
+ 结构化交接
+ 版本化成果物
+ 可复现运行
+ 证据图谱
+ 审核门禁
+ 可复用模板
= 可规模化的多 Agent 知识工作 SaaS
```

下一步最重要的工作不是继续增加功能名词，而是冻结 P0 决策，写出 Task/Handoff/Artifact/Run 的正式 Schema，并用接力式和分发式两个端到端样例验证这些契约是否足以支撑真实协作。
