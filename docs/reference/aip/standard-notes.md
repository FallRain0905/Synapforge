## 1. 第 1 部分：总体架构
来源：https://aip.openatom.tech/explore/journalism/detail/501588785172189184

- 核心是一张「智能体互联参考架构」图；编写组共识：**从"互联互通所需的功能"角度阐述架构，而非具体实现实体**——这样既能给稳定参考架构，又不束缚产业。
- 标准内容包含：智能体互联所需各功能的描述、**功能之间的接口描述**；附录给典型场景（手机终端智能体互联、机器人智能体互联）。
- 设计原则（技术特点）：
  1. 为产业界提供互联互通时**各自系统应具备的最小功能集合**；
  2. **不约束具体技术形式**（集中式、分层式、分布式皆可行）；
  3. 厂商只需具备这些功能集合并满足功能点与接口规范，即可与其他厂商互联；
  4. 遵循标准的系统既可在自有生态内运行（**局域系统**），也可开放组件接口融入大生态（**广域系统**）。
- 参考实现（北邮 ACPs 协议族）：
  - 采用**分层集中**技术方案：自治域内用集中式服务器实现管理实体（**注册服务器、身份凭证管理与验证服务器、发现服务器**），以提升可管理性与运行效率；
  - 可随时开放服务器接口与其他厂商互联互通；
  - **可兼容已采用 A2A 与 MCP 协议实现的智能体与工具**（属参考实现的性质，非标准原文承诺）；
  - 用**消息队列服务器**做消息分发，支持比 A2A 点对点"效率更高的**群组通信模式**"。
- 未给出：分层结构细节、各模块职责划分、数据/交互流程、术语定义章节（文章称后续再解读子协议）。
- 联系方式：北京邮电大学人工智能学院智能体互联小组，liujun@bupt.edu.cn

## 2. 第 2 部分：身份码
来源：https://aip.openatom.tech/explore/journalism/detail/501595031405203456

- 角色：
  - **智能体身份管理功能提供方**：可信机构，分配唯一身份码；**可以有多个**提供方；
  - **智能体注册方**：面向公众的智能体须由责任主体提交注册，可能"经审核后方可运行"。
- 两级编号：
  - **智能体程序包序列号**：智能体由程序包创建，注册时只审核程序包，得到"提供方范围内唯一"的编号；
  - **智能体实例序列号**：由已注册程序包创建的实例，自动审核，得到"提供方范围内唯一"的编号。
- 为什么需要身份码：类比身份证号——**把属性、能力、信用关联起来**，用行为记录约束社会责任。
- 是否强制：类比校园卡号 ≠ 身份证号——**只在自己可控范围内运行的智能体可以用自定义编号**，需要时再与身份码建立映射。
- 文章明确说"最核心的部分是一张表"，但**表格内容未在页面出现**（无法据此得到编码/校验规则）。

## 3. 第 3 部分：身份管理
来源：https://aip.openatom.tech/explore/journalism/detail/501597933410586624

- 三个功能实体：
  1. **智能体身份注册方**：接受注册请求、审核、**分配身份码**（例：注册服务器）；
  2. **智能体凭证发行方**：创建身份凭证并**管理、验证**（例：身份证书服务器）；
  3. **智能体身份验证方**：可由智能体**自验**（互联鉴权功能），也可为提升安全性/降低负载**委托给独立验证方**（例：身份验证服务器）。
- 附录给两套**基于 CA 证书**的参考实现：注册/核验/凭证发行 + 身份鉴别；文章称其"简洁易懂、方便易行"，同时说明业界也可用其他安全机制。
- 与身份码的关系：身份码由注册方分配。
- 未给出：信任链细节、报文与字段（图未在文本里复现）。

## 4. 第 4 部分：智能体描述
来源：https://aip.openatom.tech/explore/journalism/detail/501599532505763840

- 两张核心表：
  - **智能体属性表**：对外描述应包含的信息；文章点出"比较重要的属性为：**访问地址、访问方法、认证方法和技能**"，其中**技能属性是一个列表**；
  - **智能体技能表**：描述"对外提供服务的能力"；因大模型能力，此类定义比传统 API 接口方式**要简单很多**。
- 还定义了**智能体描述的注册流程**与**对外发布能力的过程**。
- 与后续部分的关系：具备属性/能力描述与注册发布规范后，"再配合第 5 部分的能力和流程"，智能体之间才有相互了解的平台与流程基础。

## 5. 第 5 部分：智能体发现
来源：https://aip.openatom.tech/explore/journalism/detail/504545023891738624

- 两种发现方式：
  1. **平台式发现**：可以存在独立的**智能体发现平台**，它从合作的**智能体描述管理平台**获取已注册的智能体能力信息，按请求匹配并**推荐合适的智能体**；
  2. **预置信息式发现**：在没有发现平台的环境下，或智能体用自己缓存的能力信息，把需求与目标智能体匹配。
- 基础：已注册智能体的**描述信息**构成发现的基础（承接第 4 部分的注册）。
- 产出：两种机制都给出"**与需求能力匹配的智能体列表**"，供后续协作使用。
- 未给出：目录/注册表/查询接口的机制、逐步流程、范围与权限、示例。

## 6. 第 6 部分：智能体交互
来源：https://aip.openatom.tech/explore/journalism/detail/504548191396564992

- 三种交互模式：
  1. **点对点模式**：一对一直接交互（类比两人单独聊天）；
  2. **群组模式**：面向复杂任务协作；群组可由**请求智能体发起并维护**，也可由**第三方预先配置并管理**；成员之间通过**消息分发模块**收发；
  3. **混合模式**：同时使用点对点与群组。
- 交互要素：**数据、消息、任务、会话**（文章给出关系图与 1–8 号关系表，细节留给标准正文）。
- 参考流程：点对点交换模式、群组交互模式。
- 附录 A 三种点对点实现方式：**远程调用、流式、通知**；
- 附录 B 三种协作模式：**主从模式、代理协商模式、任务订阅模式**。
- 未给出：请求-应答与多轮的细节、安全与认证、错误处理。

## 8. 补充（非标准分篇，但很有产品参考价值）

### 8.1 能力互联（深度）
来源：https://aip.openatom.tech/explore/journalism/detail/513246383113900032

- 立论：智能体互联网的本质是"**连接能力**"，连接与交换的不再是信息或关系，而是"**可被调用、组合并以结果计价的'做事能力'**"。
- 能力被抽象为**标准化服务单元**：清晰的**输入/输出**与**服务质量合约（SLA）**，以及可观测的日志与**证据链**。
- 意图驱动：用户给出意图，编排层把意图分解为子任务，动态选择模型、工具与"人在环"的智能体协作执行。
- 关键标准化环节：用**意图—输入—输出—SLA** 描述能力边界；用**证据链**记录依据；用**升级与转人工**的决策边界控制风险。
- 能力来源不止大模型通用能力，还包括**被封装为智能体的特定人类专长**（医生诊断路径、律师检索论证、交易员风控）。
- 实现要点（作者归纳）：可全网识别与追溯的**身份码**（与公钥绑定、可验证证书、签发/轮换/吊销）；**机器可读的能力描述**（输入输出、SLA、失败模式、证据与合规标签、语义化版本）；**高效发现**（权威注册目录 + 去中心化语义索引、结构化硬过滤、评测与**信誉分**）；**交互协议化**（**意图对象**表达目标、约束、**预算**、时限与**证据要求**）。
- 举例：基层医生调用专家会诊代理、小所律师调用复杂检索与案例比对代理、中小机构调用量化选股与风控代理。
